问题 1 无限创建区域的维护方式难以为继

背景与现状

区域管理的核心机制是：给定用户 zipcode，在 xysc_shop_district_zipcode 中反查出所有包含该 zipcode 且启用的规则， 按 sort_num DESC 排序，优先级最高的规则生效。这个设计本意是通过新建更高 sort_num 的规则来"覆盖"旧规则， 不需要修改旧规则的 zipcode 数据。

然而这套机制在实际运营中演变成了"每次调整都新建，旧规则永不停用"的习惯， 直接导致了以下数据现状：

分类启用规则数停用规则数备注
US 可售卖（rule_type=1）932993 条中多条为历史覆盖版本
US 可配送（rule_type=2）2361停用积压 61 条从未清理
US 亚米自营（rule_type=999）60
旧数据（rule_type=0）24024 条全部"启用"，无 sort_num，无商家绑定
CA 亚米自营（rule_type=999）10
典型问题案例：rule_id=506（名称含"CMS勿使用"）、rule_id=596（名称含"请勿使用"）这两条规则， 名字上已明确标注废弃，但 status=1 且 rule_type=1， 导致其覆盖 zipcode 范围内的用户搜索时仍会命中这两个 rule_id，影响商品可见性。

问题根源

区域规则与商品的关联关系保存在 yamibuy_im.im_item_area_mapping 表中 （item_number → zipcode_limit_id，其中 zipcode_limit_id 实为 rule_id）。 商品只与某个特定 rule_id 绑定，而不是与"某类区域逻辑"绑定。 因此运营修改区域覆盖范围时，无法在原有规则上改动（改了会影响所有绑定该规则的商品）， 只能新建一条规则，然后逐一通知商品侧重新绑定。长此以往，规则数量线性增长，没有上限。

数据膨胀的连锁影响：每新增一条启用规则，都意味着其覆盖的所有 zipcode 在 xysc_shop_district_zipcode 中增加等量行数。 目前 US 可售卖 93 条规则已产生 203 万行 zipcode 明细（去重后只有 44,337 个唯一 zipcode）， 同一个 zipcode 最多被 72 条规则重复引用，数据冗余比高达 46:1。

对下游系统的影响

  • 搜索侧（ec-search）：ES 建索引时通过 GROUP_CONCAT(rule_id) 将商品关联的所有有效 rule_id 聚合写入索引字段，规则越多，每个商品的 rule_ids 数组越长，索引体积随之增大。
  • 查询侧（ec-customer）：zipcode → rule_ids 的数据库查询需要 JOIN 一张 203 万行的大表，规则越多行数越多，查询开销持续增长（详见问题 2）。
  • 运营侧：列表页上百条规则难以辨别哪条真正生效，sort_num 手动维护极易混乱，维护成本随规则数量指数级上升。

问题 2 zipcode 查 rule_ids 的计算量随规则增长持续膨胀

完整调用链

用户每次访问搜索页、商品列表页时，系统需要确定该用户所属的区域规则，完整链路如下：

ec-search 收到搜索请求 → Feign 调用 ec-customer 的 /zipcode 接口 → ZipCodeHelper.getZipCode() 通过责任链（缓存→地址→Geo→IP→仓库）获取用户 zipcode → handleRuleIds() 调用 CustomerAddressService.selectRuleIdsByZipcode() → 执行 DB 查询（或命中 Redis 缓存）返回 rule_ids 列表 → ec-search 用 rule_ids 对 ES 做 termsQuery 过滤

DB 查询的实际代价

cache miss 时执行的 SQL 是：

SELECT a.rule_id
FROM yamibuy_master.xysc_shop_district_rule a
LEFT JOIN yamibuy_master.xysc_shop_district_zipcode b ON a.rule_id = b.rule_id
WHERE a.status = 1
  AND a.rule_type = 1
  AND b.zipcode IN (#{zipcode})
ORDER BY a.sort_num DESC

这条 SQL 要在 203 万行的 xysc_shop_district_zipcode 上做 JOIN + filter + sort。 虽然 zipcode 字段有索引，但结果集包含 93 条启用规则，JOIN 后再按 sort_num 排序，随着规则数继续增长， 单次查询的扫描行数和内存消耗都会线性放大。

缓存策略的缺陷

缓存 key 为 customer:zipcode:rules_v2:{zipcode}，以 zipcode 为维度逐条缓存，TTL 24 小时， 这在正常使用时是有效的。问题出在缓存失效环节：

  • 区域变更（新建/编辑/停用）时，通过 @CacheEvictRedis 删除缓存，key 的构造参数是传入的 zipcode 数组。
  • 一条大规则（如 rule_id=684，Express Two-Day，覆盖 37,926 个 zipcode）发生变更时， 理论上需要删除 37,926 个 Redis key。
  • 但 deleteRuleIdsCacheByZipcode 是业务层按需调用的，实际传入的 zipcode 范围是否覆盖全量， 取决于调用方的实现，存在缓存只失效了一部分，另一部分要等 24 小时自然过期的风险。
实际影响：运营在 CMS 修改完一条大规则后，部分用户（zipcode 缓存尚未失效的那批） 在接下来最长 24 小时内仍会看到旧的可售范围，区域变更的生效窗口难以预测。

多服务重复实现同一查询

ec-customer-service 和 ec-opmaster-service 各自维护了一份完全相同的 selectRuleIdsByZipcode 查询逻辑（包括相同的 SQL 和相同的 Redis 缓存结构）， 两份代码独立演进，任何一处改动都需要同步另一处，存在长期不一致的隐患。

对 ES 过滤的影响

ec-search 拿到 rule_ids 列表后，用整个列表对 ES 索引字段做 termsQuery： 

// 有 ruleIds：命中区域限购商品 OR 无区域限制的全国商品
must(
  should( termsQuery(RULE_IDS, ruleIds) )   // 区域商品
  should( mustNot(exists(RULE_IDS)) )       // 全国商品
)

一个 zipcode 对应的 rule_ids 列表越长（目前一个 zipcode 最多对应 72 条规则）， termsQuery 的 terms 数组就越大，ES 端的 filter cache 命中率下降，查询开销随之上升。

问题 3 CA 站 80 万邮编场景下现有存储模型无法承载

CA Postal Code 的结构特点

加拿大邮编（Postal Code）格式为 A1B2C3（6 位字母数字交替），全国约 85 万个唯一邮编。 但加拿大邮编有天然的地理层级结构：

层级示例说明全国数量
FSA（Forward Sortation Area）V6B前 3 位，代表一个邮政配送区约 900 个
LDU（Local Delivery Unit）3K9后 3 位，代表街道级精度85 万个
ProvinceBC（不列颠哥伦比亚省）FSA 首字母对应省份13 个

实际业务中，配送区域的定义通常是以 FSA（前 3 位）或省为单位的， 极少需要精确到每一个 LDU（街道级邮编）。

现有存储模型的问题

当前 CA 站的存储方式与 US 站完全相同：每条邮编写入 xysc_shop_district_zipcode 的一行。 目前 CA 站只有 1 条规则 1,558 条 postal code，尚未暴露问题。 一旦按全量邮编配置，数据规模将是：

场景规则数zipcode 行数估算与 US 现状对比
US 现状（可售卖启用）93203 万行基准
CA 全国单条规则185 万行相当于 US 的 41%
CA 若按商家模式建 10 条规则10850 万行超出 US 4 倍
存储与查询的双重压力：850 万行的 zipcode 表上执行 JOIN + filter + sort， 即使有索引，全表扫描的代价也将是现在的 4 倍以上。而且 6 位 CA postal code 的区分度远高于 5 位 US zipcode， 索引碎片化更严重。

冗余度问题

如果用 FSA（前 3 位）来描述区域，全国 900 个 FSA 就能覆盖 85 万个邮编， 存储量压缩 944 倍。现有模型强制按全码存储，放弃了这个天然优化空间：

存储方式描述"不列颠哥伦比亚省全境"需要的行数
当前：按 LDU 全码存储约 18 万行
优化：按 FSA 前缀存储约 190 行（BC 省约 190 个 FSA）

前端录入效率问题

目前 CA 站的录入方式是文本框批量粘贴（逗号/换行分隔），逐条正则校验。 85 万条邮编粘贴进去既不现实（页面会卡死），也不必要。 US 站有按州/县/市层级选取的交互，CA 站目前没有等价的按 Province/FSA 选取能力。

小结：CA 站扩展的核心矛盾在于——现有数据模型以"精确到每一个邮编"为前提设计， 而 CA 的业务诉求实际只需要"精确到 FSA 或省"。 如果不在模型层面做调整，简单地把 85 万条邮编灌进去，会在存储、查询、录入三个维度同时达到系统瓶颈。
