1. 功能概述

区域管理是电商平台的地理区域配置系统，允许运营人员定义特定地理范围（由一组 zipcode 或 postal code 构成），并将该范围与商家和业务类型绑定，供商品可售判断、配送校验、搜索过滤、CMS 内容定向等多条业务链路使用。

核心概念

概念说明
区域规则（Rule）一条区域记录，有唯一 rule_id，包含名称、业务类型、区域类型、绑定商家、所属站点等属性
业务类型（rule_type）1=可售卖、2=可配送、999=亚米自营配送（脚本维护，CMS 不可操作）
区域类型（area_type）1=其他、2=国家、3=大区、4=洲际、5=州内

zipcode（US）美国 5 位邮编，支持按州/县/市/直接输入 zipcode 方式批量选取；支持包含列表和排除列表
postal code（CA）加拿大 6 位邮编（格式 A1B2C3），批量文本录入，自动校验格式

5. 核心业务逻辑

5.1 新建/编辑区域 — zipcode 处理流程

US 站（checkAndGetZipcode）：

输入：stateList / countyList / cityList / zipcodeList（各取一种或多种）
         ↓
1. 分别查 xysc_zipcode 表，把州/县/市扩展为对应的 zipcode 集合
2. 合并所有来源的 zipcode，去重
3. 逐条验证 zipcode 在 DB 中是否真实存在（过滤非法码）
4. checkRepeat=true 时：查同 rule_type 下其他 status=1 规则是否有重叠 zipcode → 提示运营
5. 将 zipcode 写入 xysc_shop_district_zipcode（先删旧记录再批量插入）
6. 将 descList（包含）/ descListExclude（排除）写入 remark 字段 JSON

CA 站（checkAndGetCanadaPostcodes）：

输入：postcode_list（文本，逗号/换行分隔）
         ↓
1. postcodeNormalizer.splitInput → 按逗号/换行分割（中文逗号不分割）
2. 逐条 postcodeNormalizer.normalizeCa → 去除 Unicode 空白，转大写
3. postcodeNormalizer.isValidCa → 校验 /^[A-Z]\d[A-Z]\d[A-Z]\d$/ 正则
4. 无效码收集，最多上报 MAX_INVALID_POSTCODE_REPORT=50 个，超出截断
5. 自动去重
6. 写入 xysc_shop_district_zipcode
7. 写入 remark.postcode_list

5.2 区域优先级命中机制

规则：给定一个 zipcode，在 xysc_shop_district_zipcode 中找到所有含该 zipcode 且 status=1 的规则，按 sort_num DESC 排序，sort_num 越大的规则优先级越高。

业务含义：运营无需修改旧规则，只需新建一条 sort_num 更大的规则，该 zipcode 的用户就会优先命中新规则。新规则的 zipcode 范围可以是旧规则的子集或不同集合。 
-- ec-customer-service: selectRuleIdsByZipcode
SELECT a.rule_id
FROM yamibuy_master.xysc_shop_district_rule a
LEFT JOIN yamibuy_master.xysc_shop_district_zipcode b ON a.rule_id = b.rule_id
WHERE a.status = 1
  AND a.rule_type = 1          -- 只查可售卖，可配送和自营配送有独立查询入口
  AND b.zipcode IN (#{zipcode})
ORDER BY a.sort_num DESC       -- 优先级排序

返回的是完整 rule_id 列表（不是只取第一个），下游 ec-search 用整个列表做 ES terms 过滤：

// 商品有区域限制时，只要与用户 ruleIds 有交集即可命中
should( termsQuery(RULE_IDS, userRuleIds) )   // 有区域限制的商品
should( mustNot(exists(RULE_IDS)) )           // 全国商品（无区域限制）

5.3 站点隔离 Guard

AreaService 内置三重 Guard 方法，防止跨站操作：

  • assertRuleBelongsToCurrentSite：编辑/查看时确认 rule 的 site_code 与当前请求站点一致
  • assertCmsOperableRuleType：rule_type=999（亚米自营）的规则禁止 CMS 操作，仅脚本维护
  • assertCmsOperableRule：组合上面两项校验

5.4 操作冷静期（1小时）

启用/停用时记录 enable_dtm = 当前时间戳。前端在渲染操作按钮时，检查 enable_dtm 与当前时间的差值：若距离上次操作不足 3600 秒，按钮置灰并倒计时显示剩余秒数，防止频繁切换状态。

8. 已知问题与注意事项

8.1 标注废弃但仍启用的规则（待清理）

rule_id=506（自营冻品销售范围，CMS勿使用）和 rule_id=596（CE活动新用户，请勿使用）的 rule_type=1，status=1， 实际上仍会在 selectRuleIdsByZipcode 中被查到，对其 zipcode 范围内的用户搜索结果产生影响。 建议将这两条规则的 status 改为 0（停用）。

8.2 旧数据（rule_type=0）24 条规则保持启用

这 24 条最早期的规则（rule_id=3~33 等）没有 rule_type、没有绑定商家，均早期按商家名称命名。由于 selectRuleIdsByZipcode 的 WHERE 条件是 rule_type=1，这些规则不影响线上搜索和可售判断，但仍占用 zipcode 明细表约 4.6 万行，建议统一停用清理。

8.3 大量停用规则未清理

停用的规则共 90 条（可售卖 29 条 + 可配送 61 条），对应 zipcode 明细行数约 3 万行。停用规则不影响线上，但历史积累较多，建议定期清理。

8.4 rule_type=999（亚米自营）不受 CMS 管控

这 7 条规则（US 站 6 条 + CA 站 1 条）由脚本维护，AreaService 内置 Guard 禁止 CMS 操作。目前 CA 站的 rule_id=766（Extended Delivery Area）就是这个类型，绑定了 seller_id=5000 的加拿大仓。

8.5 CA 站区域数据极少

当前 CA 站只有 1 条区域规则（rule_id=766），CA 功能仍在建设中。前端已适配（postcodeNormalizer、isCaSite 判断），后端也已完整支持，但运营层面尚未大规模配置。

8.6 写操作入口分散

除 central-content-service 外，central-sellerportal-service（商家门户）和 central-so-service（订单后台）也能写入区域数据，三个入口写同一张表，存在维护分散的风险。

8.7 sort_num 已达 999，扩展空间有限

目前最大 sort_num=999，若继续新增高优先级覆盖规则，需注意 sort_num 上限问题（字段为 INT UNSIGNED，实际最大值可达 42 亿，不存在溢出风险；但业务约定的"最大"值需要明确管理）。
